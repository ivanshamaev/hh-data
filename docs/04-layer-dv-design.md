# 04 — Проектирование Data Vault 2.0

Здесь описывается, **зачем** в проекте введён слой Data Vault 2.0, **какие объекты** (хабы, линки, спутники) созданы и **почему** именно так, а также **где** создаётся структура (DDL).

## Зачем Data Vault 2.0

- **Нормализованное хранилище**: бизнес-ключи (вакансия, регион, работодатель, навык, роль и т.д.) в отдельных таблицах-хабах; связи многие-ко-многим и многие-к-одному — в линках; атрибуты и их история — в спутниках.
- **История и аудит**: в спутниках хранится load_dt (момент загрузки), можно восстанавливать срез на дату и отслеживать изменение атрибутов.
- **Raw DV**: без бизнес-правил — зеркально переносим структуру из источника (raw.vacancy_details / wide), что позволяет потом добавлять бизнес-слой поверх.

## Где лежит DDL DV

- **Папка**: `airflow/dags/init_db/dv_2/`
- **Файлы**: `00_schema.sql`, `01_hubs.sql`, `02_links.sql`, `03_satellites.sql`
- **DAG**: `airflow/dags/init_db/dag_init_dv2.py` — выполняет эти файлы по порядку (схема → хабы → линки → спутники).

## Схема dv

Создаётся в `00_schema.sql`. Все объекты DV лежат в схеме `dv`.

## Хабы (H_*)

Хаб — одна таблица на одну сущность по бизнес-ключу. Первичный ключ — hash от бизнес-ключа (в нашем случае MD5), плюс load_dt и record_source.

| Хаб | Бизнес-ключ | Зачем |
|-----|--------------|-------|
| **H_Vacancy** | id вакансии | Центральная сущность: одна запись на вакансию |
| **H_Area** | area.id | Регион/город из API |
| **H_Employer** | employer.id | Работодатель |
| **H_Schedule** | schedule.id | График работы (полный день и т.д.) |
| **H_Employment** | employment.id | Тип занятости (полная/частичная) |
| **H_Experience** | experience.id | Требуемый опыт |
| **H_BillingType** | billing_type.id | Тип биллинга вакансии |
| **H_EmploymentForm** | employment_form.id | Форма занятости |
| **H_ProfessionalRole** | professional_roles[].id | Профессиональная роль (из массива в ответе) |
| **H_Skill** | название из key_skills[] | Навык (массив строк/объектов в ответе) |

Так мы получаем уникальные сущности по всем измерениям, которые встречаются в деталях вакансий; повторная вставка по тому же бизнес-ключу — ON CONFLICT DO NOTHING.

## Линки (L_*)

Линк связывает два (или более) хаба. Ключ линка — hash от конкатенации ключей хабов (например, vacancy_hk || area_hk). Так фиксируются связи «вакансия — регион», «вакансия — работодатель», «вакансия — навык» и т.д.

| Линк | Связь | Зачем |
|------|--------|-------|
| **L_Vacancy_Area** | вакансия N:1 регион | У каждой вакансии один регион |
| **L_Vacancy_Employer** | вакансия N:1 работодатель | Один работодатель на вакансию |
| **L_Vacancy_Schedule** | вакансия N:1 график | Один график |
| **L_Vacancy_Employment** | вакансия N:1 тип занятости | Один тип занятости |
| **L_Vacancy_Experience** | вакансия N:1 опыт | Один уровень опыта |
| **L_Vacancy_BillingType** | вакансия N:1 тип биллинга | Один тип биллинга |
| **L_Vacancy_EmploymentForm** | вакансия N:1 форма занятости | Одна форма |
| **L_Vacancy_ProfessionalRole** | вакансия M:N роли | У вакансии может быть несколько проф. ролей |
| **L_Vacancy_Skill** | вакансия M:N навыки | У вакансии список навыков |

Линки позволяют строить аналитику по связям (например, все вакансии по навыку «Python») без дублирования атрибутов вакансии.

## Спутники (S_*)

Спутник хранит атрибуты, относящиеся к хабу (или к линку), и привязан к моменту загрузки (load_dt). Первичный ключ — (parent_hk, load_dt). Так сохраняется история изменений.

| Спутник | Родитель | Что хранит |
|---------|----------|------------|
| **S_Vacancy_Details** | H_Vacancy | Название, зарплата, адрес, даты, описание, флаги, график по дням/часам, названия ролей и т.д. |
| **S_Area_Details** | H_Area | area_name, area_url |
| **S_Employer_Details** | H_Employer | employer_name, url, logo |
| **S_Schedule_Details** | H_Schedule | schedule_name |
| **S_Employment_Details** | H_Employment | employment_name |
| **S_Experience_Details** | H_Experience | experience_name |
| **S_BillingType_Details** | H_BillingType | billing_type_name |
| **S_EmploymentForm_Details** | H_EmploymentForm | employment_form_name |
| **S_ProfessionalRole_Details** | H_ProfessionalRole | professional_role_name |

Один спутник на тип сущности — достаточно для Raw DV; при росте можно разбить спутники по темам или по частоте изменений.

## Итог

Объекты DV спроектированы по ответу API деталей вакансии (и широкой таблице как референсу полей): хабы — под каждое измерение с уникальным бизнес-ключом, линки — под связи вакансии с этими измерениями (в т.ч. M:N для ролей и навыков), спутники — под контекст и историю по каждому хабу. DAG `init_dv2` только создаёт схему и таблицы; наполнение — в разделе 05.
